# MCP 建筑场景创建与导出 Workflow 记录

## 1. 这次验证的目标

本次目标是验证：能否不通过人工点击编辑器，而是直接通过 Pascal MCP 创建一个建筑场景，并让浏览器编辑器打开这个场景进行检查。

最终结果是可以实现，但需要注意一个关键点：MCP 保存的数据库路径和浏览器应用读取的数据库路径必须一致。否则会出现“MCP 已保存，但浏览器打开时提示 Scene not found”的情况。

## 2. 本次创建出的模型内容

本次通过 MCP 创建的是一个简单的一层住宅/起居空间模型。

模型内容包括：

- 1 个场地
- 1 栋建筑
- 1 个主要楼层
- 1 个屋顶专用楼层
- 1 个矩形房间区域
- 4 面墙
- 1 块楼板
- 1 个天花板
- 1 扇门
- 2 扇窗
- 3 件家具：沙发、椅子、电视柜
- 1 个双坡屋顶

最终保存后的场景信息：

- 场景名称：`MCP Clean Demo House`
- 场景 ID：`6277f322fd6f`
- 节点数量：`19`
- 浏览器访问地址：`http://localhost:3002/scene/6277f322fd6f`
- 校验结果：`valid = true`
- 高层检查结果：`issues = []`

## 3. 从 MCP 创建建筑的实际步骤

### 第一步：创建基础场景

先通过 MCP 创建一个空白基础场景。这个模板会给出最基本的场地、建筑和楼层。

本次实际使用的是 `empty-studio` 模板。

需要注意：这个模板本身带有一组默认墙体、房间区域、门和窗。为了得到更干净的演示场景，本次后续删除了模板自带内容，再重新创建房间。

### 第二步：读取当前楼层

创建场景后，先读取楼层列表，找到主楼层 ID。后续所有墙、楼板、天花板、家具等内容都需要挂到这个楼层下。

这一步的作用是确认“建筑内容应该放在哪里”。

### 第三步：清理模板默认内容

为了避免模板默认门窗位置带来的校验问题，本次删除了模板自带的：

- 默认墙体
- 默认门
- 默认窗
- 默认房间区域

这一步不是每次都必须做。如果后续使用真正的空模板，或者从项目里提供一个更适合 MCP 建模的模板，这一步可以省略。

### 第四步：创建完整房间

使用 MCP 的房间创建能力，根据一个矩形多边形一次性生成：

- 房间区域
- 墙体
- 楼板
- 天花板

本次房间尺寸约为 8 米 × 6 米，面积约 48 平方米。

这一步是整个 workflow 的核心。它说明 MCP 不是只在场景里画一个视觉模型，而是在创建结构化建筑节点。墙、楼板、天花板、房间区域都会成为可继续编辑的对象。

### 第五步：添加门窗

房间创建完成后，再对具体墙体添加门和窗。

本次添加了：

- 1 扇门
- 2 扇窗

门窗并不是独立漂浮物，而是挂在墙体上的子节点。这样后续渲染系统可以根据门窗位置在墙体上生成洞口。

### 第六步：自动布置家具

使用 MCP 的房间家具布置能力，根据房间类型放置基础家具。

本次房间类型设置为 living，因此系统自动放置了：

- 沙发
- 椅子
- 电视柜

其中茶几因为碰撞检查被跳过。这说明 MCP 工具不是盲目放置物体，而是会尝试避免明显重叠。

### 第七步：创建屋顶

在主楼层上方创建一个屋顶专用楼层，再创建一个双坡屋顶。

本次屋顶类型是 gable roof，也就是常见的双坡屋顶。

这一步说明 MCP 可以处理不只是室内房间，还可以处理建筑外部结构。

### 第八步：校验场景

创建完成后运行两类检查：

1. 结构校验：确认每个节点是否符合 schema。
2. 高层场景检查：确认楼层、墙、门窗、楼板、天花板、屋顶等组合是否存在明显问题。

本次最终结果：

```text
valid = true
issues = []
```

这表示场景不仅数据结构合法，而且高层检查也没有发现明显问题。

## 4. 保存到浏览器可见场景时遇到的问题

第一次保存时，MCP 返回了场景 ID：`6277f322fd6f`。

但是浏览器打开后提示：

```text
Scene not found
We couldn't find a scene with id 6277f322fd6f.
```

原因是 MCP 和浏览器应用使用了不同的本地数据库路径。

当时实际情况是：

- MCP 保存到了用户目录下的 Pascal 数据库。
- 浏览器应用读取的是 Windows AppData 里的 Pascal 数据库。

所以 MCP 认为保存成功，但浏览器应用在自己的数据库里查不到这个场景。

后续处理方式是：

1. 从 MCP 数据库中读取该场景。
2. 复制到浏览器应用正在读取的数据库。
3. 再通过应用 API 确认场景存在。
4. 再打开页面确认不再出现 Scene not found。

最终浏览器可以通过下面地址打开：

```text
http://localhost:3002/scene/6277f322fd6f
```

## 5. 推荐的稳定 workflow

后续如果要稳定复现“AI 创建建筑，浏览器查看结果”，建议使用下面流程：

1. 启动浏览器编辑器。
2. 明确浏览器应用读取的 Pascal 数据库路径。
3. 让 MCP 使用同一个数据库路径。
4. 用 MCP 创建或加载场景。
5. 用 MCP 创建房间、门窗、家具、屋顶等内容。
6. 运行场景校验。
7. 保存场景。
8. 用浏览器打开 `/scene/<scene-id>`。
9. 在浏览器中继续人工检查和修改。

关键原则：MCP 和浏览器应用必须共享同一个 SceneStore。

如果后续要长期使用这个 workflow，建议在启动 MCP 和启动浏览器应用时都显式指定同一个数据目录，例如统一设置 `PASCAL_DATA_DIR` 或 `PASCAL_DB_PATH`。

## 6. 当前模型能导出什么

当前项目存在两类导出能力。

### 6.1 MCP 端导出

MCP 端目前可以导出场景 JSON。

这个 JSON 是 Pascal 自己的结构化场景图，里面保留了：

- 场地
- 建筑
- 楼层
- 墙
- 门窗
- 楼板
- 天花板
- 屋顶
- 家具
- 节点之间的父子关系

它最适合用于：

- 在 Pascal 项目中重新加载
- 调试场景内容
- 让 AI 继续修改
- 做版本记录或持久化

但它不是通用 BIM 文件。

MCP 端目前不能直接导出 GLB。项目里的 MCP `export_glb` 明确返回 `not_implemented`，原因是 GLB 导出依赖浏览器里的 Three.js 渲染器，而 MCP 是 headless 环境，没有浏览器渲染上下文。

### 6.2 浏览器端导出

浏览器编辑器里有 3D 模型导出能力。

当前支持：

- GLB
- STL
- OBJ

这些导出来自浏览器中已经渲染出来的 Three.js 场景。

含义分别是：

- GLB：适合保留 3D 模型、材质和层级，常用于网页、游戏引擎、3D 查看器。
- STL：主要是几何网格，常用于 3D 打印或简单几何交换，通常不保留复杂材质和语义。
- OBJ：常见通用 3D 网格格式，适合基础模型交换，但语义能力有限。

这些都是“3D 网格/视觉模型”导出，不等同于 BIM。

## 7. 这是不是 BIM 模型

严格来说，目前不是 BIM 模型。

当前 Pascal 场景更接近“语义化建筑场景图 + 可渲染 3D 模型”。

它比普通 mesh 更有结构，因为内部知道哪些节点是墙、门、窗、楼板、天花板、屋顶和家具。但它还没有导出成 IFC、RVT 或其他 BIM 标准格式，也没有完整实现 BIM 所需的建筑构件分类、属性集、材料规范、构造层、工程量、规范信息和跨软件互操作。

可以这样理解：

| 类型 | 当前是否支持 | 说明 |
| --- | --- | --- |
| Pascal 场景 JSON | 支持 | 最适合在本项目内保存、加载、继续编辑 |
| GLB | 浏览器端支持 | 3D 可视化模型，不是 BIM |
| STL | 浏览器端支持 | 几何网格，不是 BIM |
| OBJ | 浏览器端支持 | 通用网格模型，不是 BIM |
| IFC/BIM | 暂不支持 | 需要额外实现 BIM 映射和导出器 |

## 8. 如果要发展成 BIM，需要补什么

如果目标是未来导出 BIM，建议增加一条独立路线：IFC 导出。

需要做的事情包括：

1. 把 Pascal 的节点类型映射到 IFC 构件类型。
   - 墙映射为墙构件。
   - 门映射为门构件。
   - 窗映射为窗构件。
   - 楼板映射为楼板构件。
   - 屋顶映射为屋顶构件。

2. 为构件补充 BIM 属性。
   - 名称
   - 类型
   - 尺寸
   - 材料
   - 楼层归属
   - 空间归属
   - 构造信息

3. 建立空间关系。
   - 建筑包含楼层。
   - 楼层包含空间。
   - 空间被墙体围合。
   - 门窗开口属于对应墙体。

4. 增加 IFC 导出器。
   - 将 Pascal 场景图转换为 IFC 文件。
   - 保留建筑语义，而不是只导出视觉网格。

因此，当前项目已经具备向 BIM 发展的基础，因为它内部已经有语义化建筑节点；但当前导出结果还不能称为 BIM。

## 9. 本次结论

通过本次 workflow 可以确认：Pascal MCP 可以实际创建建筑场景，而且创建结果可以被浏览器编辑器打开和检查。

当前最可靠的保存和复用格式是 Pascal 场景 JSON。浏览器端可以导出 GLB、STL、OBJ 这类 3D 模型格式，但这些格式不是 BIM。

如果后续目标是做 AI 建筑编辑器，当前能力已经足够支撑“AI 生成场景 + 人类编辑器检查修改”的闭环。

如果后续目标是进入建筑专业软件生态，则需要继续实现 IFC/BIM 导出能力。
