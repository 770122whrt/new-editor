# Pascal Editor 项目初步 Review 周报

## 一、项目整体理解

Pascal Editor 是一个面向建筑空间设计的 3D 编辑器项目。它的目标不是只做一个能展示模型的网页，而是建立一套可以“创建、编辑、保存、自动生成建筑场景”的系统。

从使用体验上看，它希望用户能够像使用轻量级建筑编辑工具一样，在浏览器里创建墙体、楼层、门窗、屋顶、房间分区和家具，并在 2D 平面与 3D 场景之间切换。另一方面，项目还提供了 MCP 能力，使 AI 智能体也可以通过结构化工具来创建和修改建筑场景。

所以这个项目可以理解为三部分的结合：

1. 一个面向人的建筑编辑器。
2. 一个面向浏览器的 3D 建筑渲染器。
3. 一个面向 AI 的建筑场景操作接口。

## 二、项目架构的通俗说明

项目整体采用分层结构。不同层负责不同事情，避免所有逻辑都混在一起。

第一层是场景数据层。它负责定义建筑场景里有哪些对象，比如场地、建筑、楼层、墙、门、窗、楼板、天花板、屋顶、房间区域和家具。它还负责保存这些对象之间的父子关系，以及撤销、重做、增删改查等基础能力。

第二层是 3D 展示层。它负责把数据层里的建筑对象变成浏览器中能看到的 3D 画面。例如，墙体数据会被转换成墙体模型，门窗数据会影响墙上的洞口，楼板和屋顶会被转换成对应的几何形状。

第三层是编辑体验层。它负责用户实际操作时看到的工具和界面，比如画墙工具、放置门窗工具、楼层切换、平面图编辑、材质涂刷、选择高亮、辅助线和操作面板。

第四层是应用承载层。它负责网页路由、场景保存、场景加载、接口请求和本地运行环境。可以理解为把前面三层组合成一个完整应用的外壳。

这套结构的好处是：场景数据、3D 渲染、编辑交互、网页应用不会互相绑死。后续如果只想做一个只读展示器，可以复用 3D 展示层；如果想让 AI 自动建模，可以复用场景数据层和 MCP 工具；如果想继续完善浏览器编辑器，则主要扩展编辑体验层。

## 三、建筑场景是如何建立起来的

这个项目建立场景的核心思想是：先建立结构化数据，再由渲染系统把数据转换成可见的 3D 场景。

一个典型建筑场景大致会按下面的顺序形成：

1. 先创建一个场地。
2. 在场地中创建一栋建筑。
3. 在建筑中创建楼层。
4. 在楼层上创建墙体、楼板、天花板和房间区域。
5. 在墙体上添加门和窗。
6. 根据房间用途放置家具、灯具或其他物件。
7. 添加屋顶、楼梯、围栏等更复杂的结构。
8. 对整个场景进行校验、碰撞检查和保存。

这个过程有两种主要入口。

第一种是用户手动操作。用户在编辑器里选择工具，例如画墙、加门、加窗、放家具。每一次操作都会转化为对场景数据的修改。场景数据修改后，3D 画面会根据新数据重新更新。

第二种是通过 MCP 让 AI 操作。AI 不需要模拟鼠标点击，而是直接调用结构化工具。例如，可以要求它创建一个两居室户型、给某面墙加一扇门、给卧室放置床和衣柜，或者根据房间类型自动布置家具。这样，AI 实际上是在操作同一套场景数据，只是入口从“人手动编辑”变成了“工具调用”。

这也是项目比较有价值的地方：人和 AI 面对的是同一个建筑场景模型。用户可以手动调整，AI 也可以继续修改，两边不是两套割裂系统。

## 四、MCP 对场景创建的意义

MCP 是这个项目中很关键的一部分。它让建筑编辑器不只是一个前端工具，而是变成一个可以被智能体调用的建筑场景平台。

目前 MCP 能力大致覆盖这些方向：

1. 查询当前场景。
2. 创建楼层、墙体、房间和屋顶。
3. 给墙体添加门窗。
4. 在房间中放置家具。
5. 检查物体碰撞和场景有效性。
6. 保存、加载、重命名和删除场景。
7. 从图片或户型图中尝试提取空间信息。
8. 生成多个场景变体，用于快速比较方案。

这意味着后续可以尝试这样的工作流：

用户输入一句自然语言需求，例如“帮我做一个 80 平方米左右的两居室，有开放厨房和一个小阳台”。AI 可以先创建基础楼层和房间，再补墙、门窗、家具，然后通过校验工具检查结构是否合理，最后把结果保存成可继续编辑的场景。

对项目来说，这条路线非常重要。因为它把传统的“手动建模”扩展成“AI 辅助生成 + 人工精修”的工作流。

## 五、当前模型导出能力

目前这个项目已经具备一定的导出能力，但要区分“项目内部场景数据”和“通用 3D 模型文件”。

第一类是场景 JSON。MCP 可以把当前建筑场景导出为结构化 JSON。这个 JSON 会保留场地、建筑、楼层、墙体、门窗、楼板、天花板、屋顶、家具以及它们之间的关系。它最适合在 Pascal 项目内部继续保存、加载、修改，也适合让 AI 继续读取并加工。

第二类是浏览器端 3D 模型导出。浏览器编辑器可以从已经渲染出来的 3D 场景中导出模型文件，目前支持：

1. GLB
2. STL
3. OBJ

其中 GLB 是比较适合展示和交换的 3D 模型格式，能够用于网页 3D 查看器、游戏引擎或其他支持 glTF/GLB 的工具。STL 更偏几何网格和 3D 打印场景，OBJ 是常见的通用模型交换格式。

但这些格式都不等同于 BIM。当前项目还不能直接导出 IFC、RVT 等 BIM 标准文件。也就是说，它现在可以导出 3D 模型，尤其是 GLB；但如果要进入专业 BIM 软件生态，还需要额外实现 BIM/IFC 导出能力。

## 六、目前已经确认的项目状态

本次初步体验已经确认项目可以在本地启动，并且浏览器访问首页能够返回正常页面。由于当前机器环境里没有直接可用的 Bun 命令，实际启动时使用了备用方式直接运行应用服务，并临时跳过了本地数据库和第三方服务的环境变量校验。

这说明项目本身的前端入口是可运行的，但本地开发体验还需要进一步整理，尤其是 Windows 环境下的启动说明、依赖要求、环境变量说明和首次体验路径。

从代码结构看，项目的分层方向是清楚的，场景数据、编辑体验、3D 展示和应用承载之间有比较明确的边界。目前没有看到明显的“底层反向依赖上层”的严重架构问题。

## 七、目前主要问题

第一，项目文档仍然偏开发者视角。它能告诉开发者怎么安装和启动，但还没有很好地告诉新读者“启动后应该看什么、怎么完成第一个建筑场景、怎样判断项目运行成功”。

第二，本地运行说明还不够稳。项目推荐使用 Bun，但当前机器环境没有配置好 Bun，导致需要绕过标准命令启动。后续需要补充更清晰的本地环境要求。

第三，场景创建流程虽然能力比较完整，但还缺少一个面向体验的标准示例。例如“从空白场景创建一个简单房间，并添加门窗家具”的完整演示路径。

第四，MCP 能力很有潜力，但它和浏览器编辑器之间的联动流程还需要继续体验和验证。尤其是 AI 创建场景后，浏览器端如何实时查看、保存和继续人工修改，是后续值得重点验证的地方。

第五，导出能力需要进一步明确定位。当前可以导出 GLB、STL、OBJ 这类 3D 模型，也可以导出项目内部场景 JSON，但还不能导出 BIM/IFC。因此后续如果项目目标包含建筑专业软件互通，需要把 IFC/BIM 导出作为单独路线规划。

## 八、下一步建议

下一步建议优先做一个“最小可体验场景”的闭环。

这个闭环不需要一开始就覆盖所有建筑功能，而是先完成一个简单但完整的流程：

1. 启动编辑器。
2. 创建一个空白场景。
3. 创建一个楼层。
4. 画出一个矩形房间。
5. 添加一扇门和一扇窗。
6. 放置基础家具。
7. 保存场景。
8. 重新打开场景并确认内容仍然存在。
9. 尝试用 MCP 对同一个场景做一次修改。
10. 在浏览器中确认修改结果。

如果这个流程能稳定跑通，就说明项目已经具备“人类编辑 + AI 辅助建模 + 场景持久化”的基础闭环。

## 九、本周结论

Pascal Editor 当前已经具备比较清晰的产品方向和技术结构。它不是单纯的 3D 展示项目，而是一个面向建筑场景创建的编辑平台。

项目最值得继续推进的方向，是把“场景建立能力”做成一个稳定可演示的流程：用户可以手动创建建筑空间，AI 也可以通过 MCP 自动生成和修改场景，两者最终操作的是同一套场景数据。

在导出方面，项目当前已经可以支持面向展示和交换的 3D 模型导出，尤其是 GLB；同时也能保存和导出项目内部的结构化场景 JSON。不过，它目前还不是 BIM 模型导出工具，后续如果要进入建筑专业工作流，需要继续补 IFC/BIM 能力。

下一阶段的重点不应只是继续读代码，而是把项目跑起来、做出第一个标准示例场景，并把这个过程记录成可复现的体验文档。这样老师和后续参与者都能更直观地理解：这个项目到底能做什么，以及它距离完整的 AI 建筑编辑器还差哪些关键步骤。
